# 018 — icon-primary-color-bg

## Status

Draft

## Goal

Every app-icon surface (iOS icon, Android adaptive icon set, splash screen, web
favicon) uses a background gradient anchored on the app's actual primary accent
color — green `#0D8348` — instead of the current blue gradient, while keeping the
existing white pulse-glyph design unchanged.

## Why

User request: "I like the logo, but can we change the background colors to be more
reflective of the actual primary color used in the application?" The app's design
system (`src/theme.ts`) is "monochrome structure + single green accent" with
`accent: '#0D8348'` as the only brand color. The 017 icon used a blue gradient
(`#3FA8F8 → #208AEF → #1463C9`) unrelated to the palette. `app.json` echoes
`#208AEF` twice: `android.adaptiveIcon.backgroundColor` (inert fallback while
`backgroundImage` is set) and the `expo-splash-screen` plugin `backgroundColor`
(visible on every launch).

The splash change is a **deliberate full-bleed-accent choice** — the splash is held
until Clerk loads (`RootNavigator`), so `#0D8348` becomes the largest green surface
a user ever sees, hard-cutting to the white app. Same behavior as the old blue (not
a regression) and the most literal satisfaction of the request; the user can veto on
first launch.

## Approach

1. Edit `assets/images/vital-icon.svg`: gradient stops → `#1AA862` (0), `#0D8348`
   (0.5, exactly the theme accent token), `#06542D` (1). Nothing else changes (same
   gradient direction, extraction contract, glyph geometry — the generator's `GLYPH`
   bbox constants stay valid because the pulse trace is untouched).
2. Regenerate all 6 PNGs: `npm install --no-save @resvg/resvg-js@2.6.2`
   (lockfile-safe per [[022-pattern-icon-asset-pipeline]]) then
   `node scripts/generate-icons.mjs`.
3. `app.json`: both `#208AEF` occurrences → `#0D8348`.
4. Validation gate per [[022-pattern-icon-asset-pipeline]]:
   `npx expo prebuild -p ios --no-install --clean`, assert
   `ios/*/Images.xcassets/AppIcon.appiconset/` is populated, remove generated native
   dirs, `git checkout package.json` (prebuild silently rewrites npm scripts), and
   verify `package.json` + `package-lock.json` zero-diff AFTER the gate.

Rejected alternatives: (B) flat `#0D8348` fill — abandons the gradient depth of a
logo the user explicitly likes; (C) free-pick green gradient not anchored to the
token — fails "reflective of the actual primary color".

## Success criteria

1. `vital-icon.svg` gradient stops are the green ramp with the 0.5 stop exactly
   `#0D8348`; the `pulse` group is byte-identical to before.
2. All 6 PNGs (`icon.png`, `favicon.png`, `android-icon-background.png`,
   `android-icon-foreground.png`, `android-icon-monochrome.png`, `splash-icon.png`)
   regenerated by the script in the same change. The three glyph-only PNGs
   (`android-icon-foreground.png`, `android-icon-monochrome.png`, `splash-icon.png`)
   are **expected byte-identical (zero git diff)** since the glyph is untouched and
   resvg is pinned — any diff there is a tripwire (wrong resvg version or accidental
   glyph change), not noise.
3. Both `app.json` `backgroundColor` fields read `#0D8348`.
4. iOS prebuild gate passes (AppIcon.appiconset populated); generated native dirs
   removed; `package.json` + `package-lock.json` show zero diff at the end.
5. `scripts/generate-icons.mjs` is unchanged (no geometry or contract edits needed).

## Open questions

- None blocking. The lighter/darker ramp endpoints (`#1AA862` / `#06542D`) are an
  aesthetic derivation at the accent's hue; substitutable without affecting the
  criteria, which only pin the mid stop. The green-vs-blue aesthetic itself is
  irreducibly subjective — deferred to user veto on first launch.
